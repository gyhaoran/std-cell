# 可编程标准单元开发平台：可行性评估与架构方向

记录日期：2026-09-08。

状态：讨论草案，用于后续需求和架构讨论，不是已完成的软件设计或实现承诺。

评估依据：本次讨论、本地 LibreCell 提交 `f708e3a` 的静态源码检查，以及文末所列开源工具文档。尚未针对目标 Fab 的完整 PDK 执行平台原型验证、精度对比或生产验收。公开文档中的能力也不代表本机对应版本已经安装或验证。

## 1. 已明确的目标和开发前提

目标用户是 Fab 中从事标准单元设计、库开发和工艺探索的工程师。

用户提出的需求：

1. 提供足够的基础能力，允许工程师定义单元架构、器件布局和其他设计策略，用于新工艺下的单元设计探索。
2. 支持成熟工艺和已有设计方法：用户通过二次开发 API 定义工艺、Design Rules 和版图绘制行为，在已支持的扩展范围内不修改平台核心代码。
3. 优先支持平面 CMOS，FinFET 后续考虑。严格来说，FinFET 也可以用于实现 CMOS，当前范围的区别是平面器件与 FinFET 器件结构。
4. 以开源工具为基础，本地不依赖三大商业 EDA 厂商的工具完成日常开发与验证流程。

后续已经明确的开发前提：

> “基于 LibreCell”并不要求维持其现有架构。可以深度修改、重写支持不足的模块，提取有用的算法和代码，重新设计平台架构。

因此，本项目应视为一个新平台，LibreCell 是首批算法与实现的来源之一。它现有的数据结构和 API 不应成为新平台的能力上限。

以下各节中的具体模块划分、优先级和验收建议仍是待讨论方案，并非用户已经确认的全部需求。

## 2. 总体可行性结论

| 目标 | 判断 | 主要条件 |
|---|---|---|
| 工程师通过 API 构造器件、互连和单元版图 | 可行，适合早期交付 | 几何与电气语义一致，具备实际工艺插件 |
| 通过插件接入成熟平面工艺 | 可行 | 明确扩展接口、能力范围、版本兼容和插件测试 |
| 批量探索单元架构并比较面积、时序、功耗和可布线性 | 可行，有明确平台价值 | 器件模型、寄生提取和指标计算可信 |
| 部分或全部自动布局、布线 | 可行，但应逐类覆盖 | 允许模板、固定约束和人工干预，不假定所有单元一次成功 |
| 任意工艺、任意单元、任意规则下全自动得到最优版图 | 不宜作为初期承诺 | 搜索复杂度、规则表达及物理适用范围均有限制 |
| 达到 Fab 的生产交付要求 | 有条件可行，当前未证明 | 验证覆盖、模型与提取精度、参考数据及 Fab 验收 |

建议定位：

> 面向平面 CMOS 标准单元开发的可编程平台，使工艺知识和设计经验能够被表达、复用、验证和追溯。

可行性不应简化为“开源工具是否足够强”。实际成立条件是：工具能力、工艺数据、验证方法和验收标准共同满足需求。

## 3. 工艺探索的边界

### 3.1 平台适合承担的探索

在给定或明确假设的器件模型、层结构和规则下，探索：

- 单元高度、宽度栅格、器件区域和布线轨道。
- PMOS/NMOS 宽度分配、折指与器件排列。
- 源漏共享、diffusion break、接触位置和数量。
- 电源轨布局、引脚位置、引脚可接入性。
- 不同架构和规则组合对面积、寄生、时序、功耗及可布线性的影响。
- 一组单元在相同实验条件下的整体表现，而不只是单个 INV 的结果。

### 3.2 不能仅靠版图平台完成的探索

改变掺杂、氧化层厚度、材料或制造流程以后，真实器件的电气特性和可靠性如何变化，需要器件建模、工艺实验，必要时还涉及 TCAD。

平台可以接收相关模型和规则，并评价其单元级影响；不能通过修改一个最小间距或 `gate_length`，直接证明新工艺可制造或准确预测其性能。

实验结果应标识其依据：假设规则与模型、经过校准的数据，或工艺方已经认可的版本。布局成功与制造可行是不同结论。

## 4. 开源工具组合及边界

| 能力 | 初步候选 | 边界与适配工作 |
|---|---|---|
| 版图数据库、几何运算、显示与脚本绘图 | KLayout | 可复用底层能力，不必先自建完整版图编辑器 |
| DRC | [KLayout](https://www.klayout.de/doc/manual/drc_basic.html)；必要时增加 Magic 交叉检查 | 必须提供经过验证的工艺检查脚本；工具支持不等于规则全覆盖 |
| LVS | [KLayout LVS](https://www.klayout.de/doc/manual/lvs_intro.html)；或 Magic 提取后由 [Netgen](https://opencircuitdesign.com/~tim/programs/netgen/welcome.html) 比较 | 器件识别、端子、层连接、模型映射和比较策略都需按工艺定义 |
| 单元内部寄生提取 | 先评估 [Magic 电容及 RC 提取](https://www.opencircuitdesign.com/magic/howto.html)，预留其他后端 | 需要工艺提取参数、明确提取范围及精度验证 |
| 晶体管仿真与表征 | [ngspice](https://ngspice.sourceforge.io/osdi.html)；选择性复用 librecell-lib | 先确认模型兼容性、单位、工艺角和测量方法 |
| 库文件生成 | GDS/OASIS、LEF、SPICE/CDL、Liberty、Verilog 等适配器 | 各视图之间必须保持器件、端口、功能和单位的一致性 |
| 下游实际使用验证 | Yosys、OpenROAD、OpenSTA 等 | 不替代单元级验证，用于暴露综合映射、引脚接入和整库使用问题 |

重要区别：

- Netgen 的核心职责是网表比较，不是单独从任意 GDS 中提取所有器件。
- KLayout 的器件与网络提取可用于 LVS，但不能把 LVS 提取结果直接当成完整的寄生 RC 网表。
- [OpenRCX](https://openroad.readthedocs.io/en/latest/main/src/rcx/README.html) 主要面向 LEF/DEF 表示的已布线设计，不应直接视作覆盖单元内部全部晶体管级寄生的提取方案。
- Magic 的基本电容提取与详细 RC 提取不同，必须按实际版本和工艺配置选择流程。
- ngspice 的 OSDI/OpenVAF 支持不意味着能直接运行任意商业仿真器的加密模型。缺少可用模型时，需要工艺方提供或共同建立兼容模型，不能假设软件架构能解决这一阻碍。

没有商业工具不等于不能开发；没有完整规则、模型和校准依据时，也不能因开源检查结果为零错误就宣称达到生产要求。

## 5. LibreCell 的复用价值与改造依据

### 5.1 值得评估复用的部分

- 晶体管网络建图和 Euler 排列相关算法。
- 层次分区、布局启发式及候选评价思路。
- 布线图、寻路、冲突处理与约束求解实现。
- 器件绘图、GDS/LEF 输出相关的部分实现。
- 逻辑分析、仿真组织、表征与 Liberty 处理代码。

复用单位应是经测试确认的模块，而不是默认整条原有流程已经满足新平台要求。

### 5.2 本地源码中已核对的限制

| 位置 | 当前情况 | 对新平台的影响 |
|---|---|---|
| `lclayout/data_types.py` 的 `Transistor` | 保存类型、源栅漏和 W，没有完整的逐器件 L、体端和模型身份 | 新设计数据不能沿用这种信息丢失 |
| `lccommon/net_util.py` 的网表转换 | 根据模型名是否以 n 开头判断 NMOS，否则视为 PMOS | 需要显式器件注册和未知模型报错机制 |
| `data_types.py` 的 `Cell` | 直接以 `upper`、`lower` 表示两排器件 | 两排应是某种架构或算法的约束，不应成为全平台数据模型限制 |
| `standalone.py` 的 `_04_draw_transistors` | 主流程直接构造 `DefaultTransistorLayout` | 需要可注册的器件生成器接口 |
| `layout/transistor.py` | 默认图形使用工艺级 `gate_length` | 需要保留并明确处理每只器件的尺寸与合法化结果 |

## 6. 核心架构建议

### 6.1 统一设计数据，而不只是串接 SPICE 与 GDS

平台应同时维护四种互相关联的信息：

1. 电路：器件、端子、网络、模型、尺寸和参数。
2. 设计意图：相邻、对齐、共享、禁止共享、固定位置和允许交换源漏等约束。
3. 物理实现：器件图形、接触、导线、引脚、边界及它们的归属。
4. 验证与实验：规则错误、提取结果、仿真、指标及其来源。

建议从一开始明确 D/G/S/B、模型身份、L、W、总宽/每指宽约定、指数量、并联倍数、阈值及电压类别，并允许器件插件声明额外参数。未知或不支持的字段必须显式处理，不能静默丢弃。

折指后的多个物理器件应能追溯到原器件；共享扩散区应能追溯到相关端子。尺寸合法化若改变电路参数，必须记录并重新验证，不能仅修改版图而保持旧网表。

GDS 是交付与交换格式，不应是平台唯一的设计数据，也不能依赖 GDS 图形反推出全部设计意图。

### 6.2 分开工艺、架构、单元模板和算法

```text
平台核心
├── 统一设计数据、连接语义、几何服务、任务和结果管理
├── 有版本的 SDK 与插件契约
│
├── 工艺插件：器件、层、规则、绘制、提取、模型与测试
├── 架构插件：单元高度、器件区域、轨道、电源轨、边界约束
├── 单元模板：NAND、MUX、DFF 等设计方法
└── 算法与工具适配器：布局、布线、DRC、LVS、PEX、表征
```

同一工艺可以提供多种行高、不同性能目标的单元架构，不应为每种架构复制整份 PDK。

LibreCell 的算法通过适配器接入平台。更换算法时，应尽量保持工艺插件、单元模板和任务输入不变。

### 6.3 面向工程师的三层 API

| 层次 | 能力 | 用途 |
|---|---|---|
| 几何层 | 图形、层、布尔运算、变换、阵列和测量 | 表达特殊工艺细节 |
| 器件与互连层 | MOS、多指结构、共享扩散、Contact/Via 阵列、tap、导线和端口 | 组合有明确电气含义的结构 |
| 单元设计层 | 器件排序、分组、行与轨道、引脚约束和局部布线 | 固化经验、构造架构并调用算法 |

例如，“共享源漏”不能只是合并两个 Active 多边形。操作需要确认网络一致、器件与阱/注入/体偏置兼容、方向合法，并保留后续检查所需的连接语义。

插件生成结果至少应包括图形、端口及网络关联、边界、障碍区和合法接入位置。仅返回多边形会使后续布线与验证难以可靠协作。

### 6.4 三种工作方式共存

- 显式构造：工程师指定器件位置、方向和连线。
- 模板生成：从成熟结构和参数生成版图。
- 约束驱动生成：工程师指定必须满足的条件，其余由算法求解。

允许固定局部布局、保留部分连线、只自动处理剩余区域。人工调整必须能够转化为可保存的约束、模板修改或受管理的编辑记录，避免重新生成时丢失。

## 7. 工艺插件和稳定 API 的实际含义

工艺插件不应只有层号、最小宽度和最小间距，还应包含：

- 器件类别、模型映射、合法尺寸和参数解释。
- 器件、接触及其他结构的生成方法。
- 条件规则、派生层、特殊检查和例外适用条件。
- LVS 器件识别、端子连接和参数比较策略。
- 寄生提取参数、器件模型和工艺角配置。
- 规则与器件的合格、违规和边界测试样例。

规则能力应区分：

1. 生成时能够主动满足。
2. 生成后能够检查，但暂时不会自动修复。
3. 当前未覆盖，需要补充或人工验证。

DRC 检查与自动 DRC 修复是不同能力，不应以“能检查”推导出“能自动修好”。复杂规则可以通过后端脚本扩展，无须在第一版发明覆盖一切的规则语言。

稳定 API 需要版本、能力声明、插件契约测试和兼容策略。“不改工具”应承诺在公开支持的扩展范围内成立，而不是承诺所有未来器件结构永远不需要平台升级。

第一版算法可以仅处理两排器件，但底层应允许表达不同器件区域；第一版只支持平面 MOS，但参数与生成策略应归属相应器件类型。预留接口不等于已经支持 FinFET。

## 8. 验证体系与主要风险

### 8.1 检查覆盖和独立依据

每条关键规则应具有正例、反例和边界例，并关联规则来源。生成器和检查器可以共享规则数据以减少漂移，但这不是独立正确性证明。

需要人工审查、独立构造样例、参考设计及工艺方认可的结果。若没有商业工具对照，可利用规则边界样例、独立提取路径、工艺方参考数据和测量进行验证；仍应准确标注尚未确认的部分。

### 8.2 单元上下文和完整库验证

单个单元 DRC/LVS 通过还不够。应检查允许的相邻组合、镜像和翻转、阱与 implant 边界、电源轨连续性，以及 tap、filler、endcap 等配套单元。

对于没有独立体接触的单元，需要明确在何种 tap/行上下文下验证体连接；不能默认忽略体端。

外部引脚必须能被下游布线连接。较小面积不能抵消无法接入的引脚和不可接受的拥塞。

### 8.3 寄生提取与模型精度

提取流程必须明确包含哪些 R、C 和器件参数，检查单位、截断阈值、简化方法及模型与寄生的重复计入问题。

成功输出寄生网表，不代表提取精度满足目标。精度必须在约定的结构、工艺角和指标上建立依据。

### 8.4 表征和异常诊断

平台应能从失败点追溯到：

```text
单元 → 工艺角 → 时序弧 → 输入转换时间/负载点 → 仿真输入 → 日志与波形
```

区分模型加载失败、仿真不收敛、激励或状态设置错误、输出未跨阈值、测量失败和真实功能错误。

不得用 `1e31`、零值或未标注插补掩盖失败并发布为正常表征结果。组合单元、时序单元、三态等类别应分别建立有效激励和测量覆盖。

### 8.5 可复现性、保密与交付

每次实验关联工艺/规则/模型/插件版本、设计参数、工具版本、随机种子、日志及原始结果。缓存必须考虑这些输入，避免改动规则或模型后使用旧结果。

Fab 的私有 PDK、模型和单元数据应支持本地部署、受控访问和明确的导出边界。

本地 LibreCell 不同子项目出现 CERN-OHL-S、GPL、AGPL 等不同许可声明。复用前应建立许可证清单，并单独审查具体复用与交付安排；本评估不对闭源交付、生成物或客户插件的法律义务作结论。

## 9. 建议的分阶段验证

### 阶段一：一个工艺的小型完整流程

选择一个具备可用模型与验证数据的平面 CMOS 工艺。先覆盖 INV、BUF、NAND、NOR、AOI/OAI、MUX 等代表结构，再增加锁存器或 DFF 暴露时序单元的问题。

完成电路定义、版图、DRC/LVS、寄生提取、仿真/表征和库视图检查。明确成功案例、失败案例和未覆盖能力。

FreePDK45 可以继续用于教学与算法实验，但其演示成功不代表目标 Fab 工艺验证成功。

### 阶段二：证明插件化成立

接入第二个规则或器件组织方式明显不同的平面工艺，并在同一工艺下提供第二种单元架构。

建议验收条件：新增工艺与架构通过插件、模板和测试完成，不修改平台核心；显式模板和自动策略能够处理同一个代表单元。

### 阶段三：工程探索工作台

加入参数扫描、批量任务、局部人工约束、多种算法候选，以及面积、时序、功耗、寄生和可布线性比较。

通过 KLayout 集成完成查看、定位和标注，逐步补充交互能力。实验记录和失败诊断应与批量执行同步建设。

### 阶段四：整库与交付验证

扩大驱动档位、组合及时序类别，补齐物理配套单元、多工艺角表征、拼接测试和小型数字设计的实际使用验证。

建议第一版暂不包含 GPIO、SRAM、通用模拟版图、制造工艺仿真和 FinFET。上述排除项是范围建议，仍需后续确认。

## 10. 团队能力与后续待定问题

需要覆盖平台/API 工程、标准单元电路与版图、PDK 验证与表征三类能力。可以由同一成员兼任，但真实工艺工程师的参与和参考数据不可缺少。

下一次讨论建议明确：

1. 第一家试用 Fab、首个工艺、模型与验证数据的可用程度。
2. 首批单元类别、首种架构及必须支持的器件选项。
3. 初期以显式构造、模板还是自动搜索为主要工作方式。
4. 统一设计数据、几何与连接语义的最小契约。
5. 哪些规则主动约束、哪些只检查、哪些尚未覆盖。
6. Fab 对 DRC/LVS、提取、表征和交付文件的验收标准。
7. 第二个工艺与第二种架构如何用于检验插件边界。
8. 部署、保密、插件分发和开源许可安排。

暂不在缺少上述输入时给出确定的工期、精度或全自动成功率承诺。

## 12. 收束结论

允许提取、改造和重写 LibreCell 后，本项目的软件路线是成立的。应围绕工程师的设计意图和可验证结果建立新平台，让 LibreCell 的有用模块作为可替换实现接入。

最有价值的两个早期证明是：

1. 一个真实工艺能否走通可信、可复现的小型完整流程。
2. 第二个工艺能否只增加插件和测试，而不修改平台核心。

这两个条件成立后，再扩大自动化程度、单元覆盖和工艺探索规模。
