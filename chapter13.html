23.1 本教程的版本基线

Repository: /home/jasper/code/github/librecell
Branch:     anneal
Commit:     f708e3a
Package:    librecell-layout 0.0.9

本地 setup.py 约束了 klayout==0.26.*、networkx==2.*、pysmt==0.9.*、z3-solver==4.8.*、numpy==1.* 等旧依赖。它们与现代 Python 的兼容性不能想当然。

当前机器的现场状态：系统是 Python 3.12.3，现有 /home/jasper/.virtualenvs/iCell/bin/lclayout 在导入 smt_placer.py 时因缺少 z3 失败。因此教程不能声称“当前环境已开箱即用”，也不应在这个共享环境中边装边猜。

23.2 建立独立、可锁定的环境

不要为了旧依赖直接降级共享 Python，也不要把某个旧 Python 版本当成已经验证的安装配方。先区分两条路线：本书新增的 SPICE、算法和 KLayout 解析/几何实验已在当前 Python 3.12.3 环境实测；完整 lclayout 仍缺依赖，需要在你可控的独立环境中建立并验证锁文件。

cd /home/jasper/code/docs/std-cell
python examples/learning/preflight.py

# 以下只创建隔离环境，不表示依赖已安装或生成器已通过
TUTORIAL_ENV_ROOT=$(mktemp -d /tmp/stdcell-env.XXXXXX)
python -m venv "$TUTORIAL_ENV_ROOT/venv"
source "$TUTORIAL_ENV_ROOT/venv/bin/activate"
python --version
python -m pip --version

然后依据仓库要求与解释器兼容性，在该隔离环境内解决依赖；成功后冻结精确版本、安装来源和哈希，重建第二个空环境复验，再发布安装步骤。这里没有提供一个未经验证的 requirements lock。当前网络权限不允许补装 z3/pysmt，不能把这个阻塞描述为已解决。

如何继续学习：不必卡在安装整套生成器。先退出新建的空环境，回到能运行 KLayout Python API 的既有解释器，完成真实 parser 补丁和几何迁移；仅标准库的算法实验及通过命令行调用 ngspice 的仿真实验也可独立运行。它们不等价于完整 lclayout 成功。

最小环境验收

python -c "import klayout.db, networkx, numpy, z3; print('imports ok')"
lclayout --help
git -C /home/jasper/code/github/librecell rev-parse HEAD

只有三条都成功，才进入生成实验。若导入失败，先修依赖；不要用 --ignore-lvs 掩盖环境问题。

23.3 真实 CLI 参数

参数是否必需作用
--cell NAME是选择网表中的一个 .subckt
--netlist FILE是输入晶体管级 SPICE
--tech FILE是执行并加载 Python 技术文件
--output-dir DIR否，默认当前目录所有输出模块（writer）的输出目录
--placer否，默认 meta选择布局器：meta/flat/hierarchical/smt/random/hillclimb/ta
--signal-router否，默认 dijkstra选择信号布线器：dijkstra/steiner
--placement-file FILE否文件不存在时保存布局结果，存在时加载复用
--debug-routing-graph否输出布线图而不是正常布线图形，用于诊断端子和网格
--debug-smt-solver否显示 SMT 清理相关调试信息
-v/--verbose否打开 DEBUG 日志；这是布尔开关，argparse 也接受 -vv，但不会比 -v 更详细
-q/--quiet、--log FILE否控制日志
--ignore-lvs否LVS 失败仍写输出，仅限诊断，不是验收方式
本版本没有 --all-cells、通用 --debug 或 --routing-graph-file。批量生成必须自己循环明确存在的 subckt，并保留每个单元的退出码与日志。示例统一使用 -v，不把重复 v 当成多级日志。

23.4 生成第一个 INVX1

LIBRECELL_ROOT=/home/jasper/code/github/librecell
TUTORIAL_OUT=/tmp/librecell-tutorial-invx1
mkdir -p "$TUTORIAL_OUT"
cd "$LIBRECELL_ROOT/librecell-layout"

PYTHONHASHSEED=42 lclayout \
  --cell INVX1 \
  --netlist examples/cells.sp \
  --tech examples/dummy_tech.py \
  --output-dir "$TUTORIAL_OUT" \
  --placement-file "$TUTORIAL_OUT/INVX1-placement.json" \
  --placer meta \
  --signal-router dijkstra \
  --log "$TUTORIAL_OUT/INVX1.log" \
  --verbose

固定 PYTHONHASHSEED=42 是项目 README 给出的非确定性临时规避办法。它不证明所有算法完全确定；还应比较输出哈希、布局 JSON 和关键指标。

23.5 输出应当有什么

ls -lh "$TUTORIAL_OUT"
rg "Placement engine|routing|LVS result|Write GDS|Write LEF|Done" \
  "$TUTORIAL_OUT/INVX1.log"

klayout "$TUTORIAL_OUT/INVX1.gds"
文件检查内容
INVX1.gds顶层单元、DBU、层号、2 只 MOS、VDD/VSS、A/Y、通孔/接触孔与边界
INVX1.lef宏单元尺寸、站点、引脚端口；同时记录方向/用途与 OBS 的已知缺陷
INVX1.magMagic 技术名、矩形和端口；这是 dummy 配置的第三种输出
INVX1-placement.json晶体管名称、槽位坐标、翻转后的源/栅/漏
INVX1.log布局器/布线器、迭代、内部 LVS SUCCESS、输出路径和总耗时

23.6 把同一布局结果用于可比实验

--placement-file 已存在时会直接加载，因此可以只比较布线器或技术配置的改动，避免布局变化干扰：

mkdir -p /tmp/librecell-tutorial-steiner

PYTHONHASHSEED=42 lclayout \
  --cell INVX1 \
  --netlist examples/cells.sp \
  --tech examples/dummy_tech.py \
  --output-dir /tmp/librecell-tutorial-steiner \
  --placement-file /tmp/librecell-tutorial-invx1/INVX1-placement.json \
  --signal-router steiner \
  --verbose

反过来比较布局器时，应给每个布局器一个新的布局文件路径；否则程序会加载旧 JSON，导致你误以为切换布局器没有效果。

23.7 常见失败的定位顺序

现象先检查
ModuleNotFoundError: z3是否进入正确 venv，依赖是否按 lock 安装
No such circuit--cell 与 .subckt 名称；KLayout 解析会转大写
找不到 supply/ground端口是否使用代码识别的 vdd/vcc/vpwr 与 gnd/vss/vgnd/0
model 类型反了本地规则是模型名以 n 开头→NMOS，其余→PMOS
网络没有布线端点用 --debug-routing-graph 检查网格节距、偏移、包围量和端子
Failed to route合法布线图是否有通路、冲突是否过密，再比较布线器和成本
LVS failed先查端口/器件类型/开短路；--ignore-lvs 只输出诊断版图
首次运行验收记录

保存 commit、Python version、pip freeze、完整命令、退出码、日志、输出 hash 和一张逐层标注截图。只有这份记录完整，后续“改技术文件前后比较”才有可信基线。

本章检查点
  1. 为什么不能在已有布局 JSON 时比较布局器？
  2. 为什么 --ignore-lvs 不能出现在发布流水线？
  3. 本地 dummy tech 实际写出哪三种物理文件？
参考答案

已有 JSON 会绕过布局器并直接加载。--ignore-lvs 会让不匹配版图继续输出，破坏正确性门禁。当前配置写 GDS、LEF 和 MAG。
